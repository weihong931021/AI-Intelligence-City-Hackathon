# AI 輔助不動產估價案件審查

2026 新北市 AI 智慧城市黑客松競賽｜**地政局組**參賽專案。

決賽：2026/09/12–09/13，新北市政府 603 大禮堂。

## 題目

不動產估價案件在審查時，需依估價師填寫的估價書表，逐一檢核其是否依「評價因素基準明細表」正確判定優劣等級及修正率。審查人員必須人工比對多張表單（地價區段勘查表、影響地價區域因素分析明細表、比較法調查估價表），逐項核算距離、級距、修正率與加總結果。

命題文件指出的痛點：

1. 估價書表涉及表單眾多，人工逐項比對耗時且易發生疏漏。
2. 區域因素與個別因素需依不同用地類別基準明細表判定，人工判讀一致性不易維持。
3. 修正率加總及跨表抄填（如區域因素總修正數）容易出現計算或填載錯誤。

## 解法

系統接收**已填寫完成**的估價書表，依評價基準與作業手冊逐項重算，指出等級誤判、修正率錯誤、加總錯誤與跨表不一致，並對每項發現附上計算過程與依據頁碼。

設計上最重要的一條界線：**數值由程式決定，文字由模型生成。**

```text
輸入層    表1 勘查表 ／ 表5 區域因素分析明細表 ／ 表4 比較法調查估價表
            │
規則庫    評價基準（上限值＋級距定義）、作業手冊（切塊＋頁碼）
            │
審查引擎  純函式、無 I/O、可完整單元測試 → Finding 清單
            │
說明層    Amazon Bedrock：把 Finding 轉成說明並引用出處，不產生任何數字
            │
呈現層    三表對照、標紅定位、逐項確認、匯出勘查表
```

### 關鍵發現：修正率矩陣可由公式生成

評價基準明細表中每個修正細項都是一張「比準地等級 × 比較標的等級」的修正百分比矩陣。經核對官方範例表，該矩陣為等差且反對稱：

```text
修正百分比 = (比較標的等級序 − 比準地等級序) × Max ÷ (等級數 − 1)
等級序：優 0、稍優 1、普通 2、稍劣 3、劣 4
```

以官方基準表多個細項核對均吻合 — 容積率（上限 40，級距 10）、主要道路寬度（15 → 3.75）、站牌（8 → 2）、接近市場（6 → 1.5）、接近觀光遊憩設施（3 → 0.75）、停車場地（4 → 1）；僅有兩級的「都市計畫內外」（上限 20）則為 ÷1 = 20。

因此規則庫不必人工抄寫約 25 張 5×5 矩陣（約 600 個數值），只需抄錄每個細項的上限值與 5 段級距定義（約 25 列）。

命題文件明載「各案件之基準明細表內容可能因個案特性調整」，故公式僅作為預設生成器：建置規則庫時須對官方基準表逐格回歸比對，任何不符的儲存格一律以官方數值寫入 override 並記錄。

### 審查引擎檢查層

| 層 | 檢查內容 |
|---|---|
| L1 | 由原始條件依級距定義重新判定優劣等級 |
| L2 | 依修正率矩陣重算應得修正率 |
| L3 | 重算各主要項目的百分比小計 |
| L4 | 重算影響地價區域因素總修正數 |
| L5 | 跨表一致性：表1 原始條件 ↔ 表5 等級；表5 總修正數 ↔ 表4 區域因素調整百分率 |
| L6 | 表4「合計」與「調整百分率絕對值加總」的混用與對調偵測 |
| L7 | 價格驗算：調整至基準日單價、試算價格 |
| L8 | 免修正符號 `−` 與 `0.00` 混用、同因素重複修正、缺漏值被當 0 |

官方範例案件（金山區 P002-00、案號 1140901-99-001）本身即為回歸基準：

```text
184,763 × (1 + 0.02) = 188,459   ← 交易日期調整
188,459 × (1 + 0.13) = 212,958   ← 個別因素合計
```

兩式與書表範本記載值一致。

## 開發

需求：Python 3.12+，無外部相依套件（測試使用標準函式庫 `unittest`）。

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -t .
```

目前 65 個測試全數通過，涵蓋既有的資料匯入模組。審查引擎的測試將隨 [任務計畫](.kiro/specs/appraisal-review-assistant/tasks.md) 逐步加入。

### 開發限制

- 基礎模型**僅限使用 AWS 服務提供者**（依錄取信及競賽附則）。
- 提交前確認未包含 AWS Access Keys、API Tokens、資料庫密碼等憑證；憑證一律以環境變數管理。
